## 1. What A2A is

**Agent2Agent (A2A)** is an **open protocol** that lets AI agents built with **different frameworks, by different vendors**, discover each other's capabilities and **collaborate on tasks**, without sharing their internal memory, tools or code.

**History & governance:** Google launched it in April 2025 and donated it to the **Linux Foundation** in June 2025. IBM's Agent Communication Protocol (ACP) merged into it in August 2025. It now sits in the **Agentic AI Foundation (AAIF)** alongside MCP. **A2A v1.0** was finalised in March 2026.

**Why:** enterprises will run many agents (HR agent from one vendor, IT agent built in-house on LangGraph, travel agent on Microsoft Foundry...). Without a standard they can't work together. A2A is the common language.

## 2. Design principles

- **Agents stay opaque:** a client agent sees a remote agent's **skills**, not its prompts, tools or memory (this protects IP and security).
- **Built on existing web standards:** HTTP, JSON-RPC, gRPC, server-sent events, OAuth/OpenID Connect.
- **Long-running work:** tasks can take seconds or days, with status updates and human input along the way.
- **Modality-agnostic:** text, files, structured data, and more.
- **Enterprise-ready security:** authentication declared up front, standard auth schemes.

## 3. Core concepts

| Concept | What it is |
|---|---|
| **Agent Card** | A JSON "business card" describing the agent: name, description, skills, endpoint URL and bindings, capabilities (streaming, push), and auth requirements |
| **Client agent** | The agent that sends a task |
| **Remote (server) agent** | The agent that does the task |
| **Message** | One turn of communication (role: user or agent), made of **parts** |
| **Part** | A content piece: **text**, **raw bytes/file**, **URL**, or **structured data (JSON)** |
| **Task** | The unit of work, with an ID, a **context ID** (groups related tasks), a state, history and artifacts |
| **Artifact** | An output the task produces (a report, a file, JSON) |
| **Context** | Groups related tasks and messages into one conversation |

## 4. Task lifecycle & states

```
SUBMITTED ──► WORKING ──┬──► COMPLETED   ✅ (terminal)
                        ├──► FAILED      ❌ (terminal)
                        ├──► CANCELED    ⛔ (terminal)
                        ├──► REJECTED    🚫 (terminal: agent declined the task)
                        ├──► INPUT_REQUIRED  ⏸ (needs more info from the client/user) ──► WORKING
                        └──► AUTH_REQUIRED   🔐 (needs extra authorisation) ──► WORKING
```

The client sends a **message**. The remote agent replies either with a quick **message** (simple answers) or with a **task** that moves through these states and produces **artifacts**.

## 5. Discovery: the Agent Card

Agents publish their card at a well-known URL:
```
https://travel.contoso.com/.well-known/agent-card.json
```
(Clients can also get cards from a registry or catalog. Version 0.3 used `agent.json`.)

**Simplified example:**
```json
{
  "name": "Contoso Travel Agent",
  "description": "Books flights and hotels within Contoso travel policy.",
  "version": "1.2.0",
  "supportedInterfaces": [
    {"url": "https://travel.contoso.com/a2a", "protocolBinding": "JSONRPC"}
  ],
  "capabilities": {"streaming": true, "pushNotifications": true},
  "securitySchemes": {"entra": {"type": "openIdConnect", "openIdConnectUrl": "https://login.microsoftonline.com/<tenant>/v2.0/.well-known/openid-configuration"}},
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    {"id": "book-trip", "name": "Book a business trip",
     "description": "Find and book flights and hotels for given dates and destination.",
     "tags": ["travel", "booking"], "examples": ["Book me a trip to Seattle 3-5 June"]}
  ]
}
```
(Field names are simplified for teaching. Check the current spec for the exact schema.)

## 6. Interaction modes

| Mode | How | Use |
|---|---|---|
| **Request/response** | `SendMessage` waits until the task completes or needs input (or returns immediately if asked) | Quick tasks |
| **Streaming** | `SendStreamingMessage` streams task status updates and artifact chunks (if `capabilities.streaming` is true) | Real-time progress |
| **Push notifications** | The client registers a **webhook**; the agent POSTs updates when state changes | Long-running tasks (hours or days), disconnected clients |
| **Polling** | `GetTask` to check status | Simple clients |

Other operations: **cancel** a task, **list** tasks, **resubscribe** to a stream.

## 7. Protocol bindings

The card lists `supportedInterfaces` in order of preference. The client picks the first one it supports:

| Binding | Notes |
|---|---|
| **JSON-RPC 2.0 over HTTP** | The original and most common |
| **gRPC** | High performance, typed (protobuf) |
| **HTTP + JSON (REST)** | Simple REST-style endpoints |

All bindings must behave the same. Clients send an **`A2A-Version: 1.0`** header (a missing header means 0.3).

## 8. Security

- **Authentication is declared in the Agent Card** (OAuth 2.0 / OpenID Connect, API keys, mTLS), and credentials are sent in standard HTTP headers. Identity is never sent inside A2A messages.
- **Serve the public card separately** from the authenticated endpoint; an *extended* card can reveal more skills to authenticated clients.
- **Authorise per skill:** the remote agent checks what *this* caller may do.
- **Push-notification safety:** validate webhook URLs (refuse private IP ranges to prevent SSRF), authenticate webhook calls, and handle duplicate deliveries.
- **Treat incoming messages as untrusted input:** prompt injection can travel between agents.
- **Audit:** log task IDs, callers and outcomes across agents (tracing with OpenTelemetry).

## 9. A2A + MCP together

```
                        ┌─────────────────── Employee asks in Teams ───────────────────┐
                        │  "Plan my Seattle offsite and book travel"                    │
                        └──────────────────────────────┬───────────────────────────────┘
                                                       ▼
                                    Orchestrator agent (e.g. LangGraph / Foundry)
                                     │ A2A                │ A2A                  │ MCP
                                     ▼                    ▼                      ▼
                         Travel agent (vendor)   Finance agent (in-house)   Calendar MCP server
                           │ MCP                    │ MCP
                           ▼                        ▼
                      Booking API server        ERP / budget DB server
```

**Rule of thumb:** use **MCP** when you want the model to call a specific function you control. Use **A2A** when you want another *agent*, with its own reasoning and tools, to own a goal.

## 10. SDKs & platform support

- **Official SDKs:** Python (`a2a` package; client helpers such as `A2ACardResolver`), JavaScript/TypeScript (`@a2a-js/sdk`), Java, Go, .NET.
- **Frameworks:** Google ADK, LangGraph, CrewAI, Semantic Kernel / Microsoft Agent Framework, BeeAI and others can expose or call A2A agents.
- **Cloud platforms:** Microsoft Foundry Agent Service and Copilot Studio, Google Vertex AI Agent Engine, and Amazon Bedrock AgentCore Runtime support A2A agents. Check each platform's docs for current status.

**Typical Python client flow (pseudocode, check the SDK docs for exact names in your version):**
```python
# 1. Discover: fetch https://agent.example.com/.well-known/agent-card.json
card = await A2ACardResolver(http_client, base_url).get_agent_card()
# 2. Connect using the card's preferred binding, then send a message
client = create_client(card)
async for event in client.send_message(text_message("Book a trip to Seattle 3-5 June")):
    print(event)   # task status updates (WORKING, INPUT_REQUIRED...) and artifacts
```

## 💬 Interview questions & answers

**Q1. What is A2A in one sentence?**
An open protocol that lets independent AI agents, built by different teams or vendors, discover each other via Agent Cards and collaborate on tasks over standard web protocols, without exposing their internals.

**Q2. What's in an Agent Card?**
Identity (name, description, version), endpoints and protocol bindings, capabilities (streaming, push notifications), supported input/output types, security schemes, and a list of skills with descriptions and examples.

**Q3. Describe the A2A task lifecycle.**
SUBMITTED → WORKING → a terminal state (COMPLETED, FAILED, CANCELED, REJECTED), or an interrupted state (INPUT_REQUIRED, AUTH_REQUIRED) that resumes to WORKING once the client provides what's needed.

**Q4. How does A2A handle a task that takes two days?**
The client registers a push-notification webhook, or polls/resubscribes. The remote agent keeps the task state and sends updates when its status changes or artifacts are ready.

**Q5. A2A vs MCP: when do you use each?**
MCP when the agent needs a tool or data source it directly controls. A2A when you delegate a goal to another autonomous agent that decides how to achieve it. They're complementary: A2A agents commonly use MCP internally.

**Q6. Why are A2A agents "opaque"?**
Each agent keeps its prompts, tools, memory and data private and only advertises skills. This protects intellectual property, reduces the attack surface, and lets vendors' agents interoperate safely.

**Q7. What are the key A2A security concerns?**
Authenticating and authorising callers per skill, protecting extended agent cards, preventing SSRF through push-notification URLs, prompt injection passed between agents, and end-to-end audit tracing.
